# 04 数据模型

> **唯一写入者**：只有归档器可写入持久层。

---

## 一、SQLite 表结构

### 1.1 events 表（14 列）

| 列名 | 类型 | 说明 |
|------|------|------|
| `id` | INTEGER | 自增主键 |
| `system` | TEXT | 系统名称 |
| `event_type` | TEXT | 事件类型 |
| `payload` | JSON | 事件载荷 |
| `content_hash` | TEXT | 内容哈希 |
| `prev_hash` | TEXT | 前一条记录哈希 |
| `curr_hash` | TEXT | 当前记录哈希 |
| `timestamp` | REAL | 事件时间戳 |
| `integrity` | TEXT | pending/verified/corrupted/rebooted |
| `chain_status` | TEXT | linked/broken |
| `integrity_score` | REAL | 0.0-1.0 |
| `ttl_protected` | INTEGER | 0=可清理，1=受保护 |
| `monotonic_ms` | REAL | 单调递增毫秒时间戳 |
| `lamport` | INTEGER | Lamport 时钟值 |

### 1.2 其他表

| 表名 | 用途 |
|------|------|
| `system_pid` | 系统进程注册 |
| `diagnoses_YYYY` | 诊断记录（按年分区） |
| `expectations` | 预期事件声明 |
| `probe_health` | 探针健康指标 |

---

## 二、哈希链协议

```
content = json.dumps({"system": ..., "event_type": ..., "payload": ..., "timestamp": ...}, sort_keys=True)
curr_hash = SHA-256(prev_hash + content)  # 完整 64 位十六进制
```

---

## 三、完整性状态

| 状态 | 含义 |
|------|------|
| `pending` | 刚归档，未验证 |
| `verified` | 哈希链已验证 |
| `corrupted` | 哈希链断裂 |
| `rebooted` | 链重启后的锚点事件 |

---

## 四、链重启协议

1. 断裂记录保持 `integrity='corrupted'`（永不修改）
2. 下一条有效记录的 `prev_hash` = `'chain_reboot_' + 上一条 curr_hash[:48]`
3. 归档器自动插入 `__chain_reboot__` 锚点事件
4. 新链从锚点开始

---

## 五、数据保留策略

| 数据类型 | 保留策略 |
|----------|----------|
| hot/*.jsonl | 归档后移至 cold/ |
| cold/*.jsonl | 永久（手动清理） |
| events 表 | 90 天 TTL，被诊断引用的事件受保护 |
| system_pid | 永久 |
| diagnoses_YYYY | 永久 |
| expectations | fulfilled=1 时清理 |
| probe_health | 最近 30 天 |

---

## 六、MySQL 表结构（Cluster 模式）

Cluster 模式使用 MySQL `wq_events` 表，字段与 SQLite events 表对齐，外加：

| 额外字段 | 类型 | 说明 |
|----------|------|------|
| `project_id` | VARCHAR(64) | 项目 ID（分布式多租户） |
| `created_at` | DATETIME | 归档时间 |

---

## 七、完整性评分

归档器每 flush 时计算完整性评分：

| 条件 | 评分 |
|------|------|
| 哈希链连续 | 1.0 |
| 哈希链断裂 | 0.0 |
| 链重启后首条 | 0.5 |
| payload 缺失关键字段 | 降级 |

---

**证据链哲学：SHA-256 哈希链，完整性评分，链重启协议。**
